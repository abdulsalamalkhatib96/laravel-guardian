# GUA-002 — Unsafe Eloquent read-modify-write

**Default severity:** HIGH. Configured critical fields can escalate to CRITICAL.

## Failure mode

Two workers read the same state, derive independent decisions, and both persist results. The code can pass all ordinary request tests while losing updates or executing a state transition twice in production.

## Unsafe arithmetic RMW

```php
$wallet = Wallet::findOrFail($id);
$wallet->balance += $amount;
$wallet->save();
```

## Unsafe check-then-act

```php
if ($withdrawal->status === 'pending') {
    $withdrawal->status = 'approved';
    $withdrawal->save();
}
```

## Safe pessimistic lock

```php
DB::transaction(function () use ($id, $amount) {
    $wallet = Wallet::query()->lockForUpdate()->findOrFail($id);
    $wallet->balance += $amount;
    $wallet->save();
});
```

`lockForUpdate()` outside the protecting transaction does not satisfy the rule.

## Safe fixed atomic delta

```php
Wallet::whereKey($id)->increment('balance', $amount);
```

## Not safe: stale derived delta

```php
$wallet = Wallet::findOrFail($id);
$delta = $target - $wallet->balance;
$wallet->increment('balance', $delta);
```

The SQL update is atomic, but the intended target depends on a stale read.

## Safe state transition

```php
$changed = Withdrawal::query()
    ->whereKey($id)
    ->where('status', 'pending')
    ->update(['status' => 'approved']);

if ($changed !== 1) {
    throw new AlreadyProcessedException();
}
```

This is a compare-and-swap pattern: the mutation itself contains the expected old state.

## Configuration

Mark business-critical fields to raise severity:

```php
'critical_fields' => [
    App\Models\Wallet::class => ['balance'],
    App\Models\Withdrawal::class => ['status'],
],
```

## Limitations

Guardian V1 does not perform full symbolic execution across arbitrary helper methods. It prefers a missed low-confidence path over reporting every model mutation as unsafe.
